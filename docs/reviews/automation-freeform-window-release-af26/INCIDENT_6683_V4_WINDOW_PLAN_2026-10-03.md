## Falha e retorno

Antes de `stop-pair`, restaurar controles iniciais e, se aplicável, retirar apenas o fence parcialmente instalado após verificar processos originais. Depois de `stop-pair`, manter guarda fechada e contenção. Se API nova não iniciou, `return-partial` prova a ausência antiga e inicia API af26 + worker mínimo af26. Se API nova iniciou, mas worker não, `return-partial` comprova saída da API candidata antes de iniciar API af26; prova V4 nova antes do worker. Se ambos iniciaram e for necessário voltar, `return` para o par sequencialmente, mantendo o frontend af26 intocado. Cada modo usa sua configuração privada e seu próprio nonce/certificado; não mover marcadores entre modos. Um observer indisponível após a API impede **também** o start do worker de retorno até que sua leitura fixa seja restaurada; conservar contenção e um único proprietário, sem bypass. Sobrevivente, socket/backend/lock inesperado ou frontend alterado bloqueia sucessor e abertura. Não matar chamada por prazo, apagar lock/auth, repetir start incerto, restaurar dump sobre dados novos ou reenviar protocolo FAILED.

No retorno, selecionar `M="$P/return-partial"` se a ida ficou parcial, ou `M="$P/return"` se API e worker candidatos já iniciaram. Após prova nova de cada ação, o executor usa `python3 "$M/delegated.py" execute recover-partial "$M"` **somente** no primeiro modo, ou `... execute stop-pair "$M"` **somente** no segundo. Prossegue, com duas provas novas separadas e check V4 antes do worker, usando `... execute start:re7-whatsapp-agent "$M"` e depois `... execute start:re7-whatsapp-web-worker "$M"`. Seguem `unfence`, verificação e restauração de controles conforme a mesma ordem acima. Se o start anterior tem intent sem resultado certo, confirmar processo/descendentes antes de escolher o modo; nunca repetir o start na ida.

O horizonte de escalonamento deve ser decidido pelo owner na janela; não é promessa de recuperação nem autorização para kill. A interrupção alcança API de todos os tenants e entradas 3000/3001, inclusive Inbox/CRM/auth/realtime/webhooks; o worker também para temporariamente, mas o frontend continua em execução atrás da contenção.
